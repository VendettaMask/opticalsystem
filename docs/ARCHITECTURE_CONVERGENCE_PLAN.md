## 1. 原问题定性（历史基线）

以下内容描述 2026-08-02 的双轨风险，用于保留迁移动机；其中“旧模型仍承担生产职责”已在 2026-08-24 修正。当时的问题不是“大量随机垃圾代码”，也不只是普通的重复代码。项目已经建立 `WorkbenchApplication`、领域服务接口和 `WorkspaceCoordinator`，但旧的 `OpticalWorkspaceModel` 仍然承担状态、文档、处方、分析、优化、公差和多配置等生产职责。结果是：

- 新架构已经成为 GUI 的公开入口；
- 旧架构仍是新服务内部的状态容器和执行器；
- 部分测试和兼容入口可以绕过新服务，直接执行旧模型；
- 新旧入口可能使用不同的默认值、请求归一化、快照时机、修订号、缓存和失效规则。

因此，风险不在于“代码看起来重复”，而在于两套控制流同时有效。同一个镜头可能因入口不同而得到不同结果，并且这种差异很难从界面或结果对象中追溯。

## 2. 2026-08-02 事实基线（历史）

以下结论来自 2026-08-02 的代码静态检查：

1. `WorkbenchApplication` 已是组合根，并向 App 提供文档、处方、分析、可视化、优化、公差和多配置服务。
2. `OpticContext` 仍直接创建并持有 `OpticalWorkspaceModel`。
3. `WorkspaceCoordinator` 和 `WorkbenchServiceBase` 通过 `Connector` 暴露旧模型；新服务普遍以旧模型作为实际执行主体。
4. `AnalysisService` 会复制 `Optic` 快照，再创建新的 `OpticalWorkspaceModel` 执行 `BuildAnalysisView`。
5. `TolerancingService` 也存在为快照创建 `OpticalWorkspaceModel` 的路径。
6. `OpticalDocumentService` 直接调用旧模型的静态读写和实例状态方法。
7. `OptilandConnector` 本身虽然是无新增方法的薄子类，但它继承的 `OpticalWorkspaceModel` 并不薄；把前者称为“薄外观”不能证明旧运行链路已经退出。
8. 生产代码中有 30 个 C# 文件直接属于或引用旧架构相关类型，其中 `OpticalWorkspaceModel` 由 14 个分部文件组成。
9. 至少 8 个测试文件直接引用旧架构，`AnalysisGuiContractTests` 等测试大量直接构造 `OptilandConnector`。这使测试可能验证旧入口，却未证明 GUI 的新入口与旧入口一致。
10. 现有 `LayeringArchitectureTests.LegacyConnectorIsAThinCompatibilityFacade` 只检查 `OptilandConnector` 自身没有声明方法，没有检查其基类是否仍承担生产逻辑，也没有阻止新服务依赖 `Legacy` 命名空间。

### 2.1 2026-08-24 迁移后事实

1. `OpticContext` 和 `WorkspaceCoordinator` 只公开 `WorkbenchRuntime Runtime`，不再公开 `Connector`。
2. Application Services 中对 `Application.Legacy`、`OpticalWorkspaceModel` 和 `Connector.` 的引用均为零，并由架构测试持续扫描。
3. `AnalysisService` 和 `TolerancingService` 的隔离快照 worker 构造规范 `WorkbenchRuntime`。
4. 原 14 个 `OpticalWorkspaceModel` 分部已迁入 `Application/Runtime/WorkbenchRuntime.*`；不存在另一套旧模型实现。
5. `OptilandConnector` 仍可被兼容测试和外部源码构造，但该类型没有声明方法，基类明确为 `WorkbenchRuntime`。
6. 当前剩余工作是进一步拆分单体运行时职责、建立独立兼容程序集和最终删除兼容 API；这些是维护性与兼容生命周期工作，不构成两条生产执行链。

### 2.2 历史审计与当前复核

历史审计材料只作为线索，不作为当前事实。早期材料中关于 `PlaceholderAnalysis`、`AnalysisRunner`、旧 `IRayAimer` 和 `SimpleOptimizer` “仍然存在”的描述已经失效；这些入口现已删除。本文后续阶段说明的是迁移计划和历史风险，不得解释为这些已删除类型仍在当前代码中。

2026-08-02 对当前代码逐项复核后的结论如下：

- 已证实并修正：`SurfaceGroup` 的破坏性组件重建、Legacy 几何同步副本、表面追迹双流程、入口瞳旧矩阵、光阑瞄准死参数、`SimpleOptimizer`、未规范化请求指纹、Full Field 全失败伪零、RMS Field Map 错误元数据和无语义图表 fallback。
- 后续已修正：材料名称解析继续由持有目录的领域服务负责；Workbench 分析元数据已统一，参数定义和产品预设构造已迁入规范 `WorkbenchRuntime`，`OpticalWorkspaceModel` 已退出。
- 不能按缺陷直接修改：Semi-Diameter 与 `PhysicalAperture` 是机械包络和光学裁剪两个概念；Telecentric 的两个字段对应外部格式中的不同键。除非取得格式语义证据和兼容迁移方案，否则不得为了减少字段数而合并。
- 需要语义证据后再迁移：Telecentric 模式枚举会改变外部序列化及编辑契约，必须先取得上游字段定义，并建立导入、保存、重新打开和追迹等价测试。

2026-08-24 的实际依赖关系可概括为：

```text
App / GUI
  -> IWorkbenchApplication
    -> 新领域服务
      -> WorkspaceCoordinator
        -> WorkbenchRuntime（唯一应用运行时）
          -> Core Optic / Analysis / Optimization / Tolerancing

兼容入口与兼容测试
  -> OptilandConnector
    -> WorkbenchRuntime（与生产服务相同实现）
```

因此生产执行已经是单轨结构。兼容类型仍存在，但没有独立状态、算法、默认值或缓存；它的最终删除仍按兼容生命周期推进。

## 3. 目标架构

收敛完成后，运行时只保留一条规范链路：

```text
App / CLI / 兼容适配器 / 测试
  -> Application Contracts
    -> WorkbenchApplication 与领域服务
      -> WorkspaceCoordinator（唯一写入、修订和生命周期协调者）
        -> Core 领域能力与规范执行器
```

必须满足以下约束：

- `Optic` 只有一个受控的工作区所有者。
- 所有修改必须通过 `WorkspaceCoordinator`，统一完成校验、撤销/重做、修订递增、缓存失效、自动半口径刷新和事件发布。
- 每类分析只有一个规范请求模型、一个默认值来源、一个名称到类型的解析入口和一个执行器。
- 文档导入、保存和多配置切换使用同一套归一化与生命周期规则。
- 优化、公差和可视化只能消费规范快照，不能自行重建另一套工作区语义。
- 兼容层只能做参数映射、返回值映射和弃用提示，不能保存独立状态、计算、缓存或默认值。
- 同一输入的结果一致性由自动化测试证明，不能依赖“目前看起来一样”。

## 4. 一致性契约

所有入口必须遵守下面的结果身份：

```text
结果身份 = 镜头内容指纹
         + 工作区修订号
         + 规范请求指纹
         + 数值后端
         + 算法版本/兼容配置
```

“同一个镜头得到同一个结果”具体表示：

1. 入口提交的参数先转换为同一个规范请求 DTO。
2. 未显式填写的值来自同一个应用预设，不允许旧入口和新入口各自补默认值。
3. 计算使用同一份不可变镜头快照及同一修订号。
4. 缓存键只由影响结果的结构化数据组成，不包含本地化名称或入口名称。
5. 结果必须携带来源修订号、规范分析键、请求指纹和执行器版本，便于定位差异。
6. 兼容入口与新入口在映射后的 DTO、轴量纲、单位、有效/无效状态和数值容差内一致。

不允许通过扩大容差、隐藏字段、跳过失败样本或删除旧入口测试来制造“一致”。

## 5. 风险清单

| 风险 | 典型表现 | 必须统一的责任 |
| --- | --- | --- |
| 默认值分叉 | 同一分析在不同入口采用不同采样、视场或参考方式 | 应用预设与规范请求生成 |
| 名称解析分叉 | 本地化标题、旧名称和规范键映射到不同分析 | `AnalysisCatalog` 与唯一解析器 |
| 状态分叉 | 一个入口修改当前 `Optic`，另一个仍计算旧快照 | 工作区所有权、修订号和取消令牌 |
| 缓存分叉 | 缓存键、缓存生命周期或快照分离时机不同 | 统一缓存策略与失效规则 |
| 文档分叉 | 打开/保存/多配置恢复走不同规范化规则 | 文档服务与格式适配器 |
| 变更副作用分叉 | 自动半口径、撤销/重做、事件发布只在部分入口执行 | 唯一写入协调器 |
| 并发分叉 | 分析、公差和优化各自创建工作模型并嵌套并行 | 统一任务生命周期与并行所有权 |
| DTO 映射分叉 | 相同 Core 结果被映射成不同轴、单位或状态 | 单一结果映射器 |
| 测试盲区 | 旧入口测试通过，但 GUI 新入口未执行同一路径 | 跨入口契约测试与架构测试 |

## 6. 实施原则

1. 先建立观测和一致性闸门，再迁移实现。
2. 一次只迁移一个领域，不进行全仓库“大爆炸重写”。
3. 迁移期间不同时改变数值算法；结构收敛和算法修正必须拆开。
4. 先把行为移到规范执行器，再让旧 API 委托，最后删除旧代码；不能只移动文件或改命名空间。
5. 每个旧入口必须登记为“委托、仅测试、待删除”三者之一，并有责任人和删除条件。
6. 每个临时兼容开关必须有到期版本，禁止形成第三条长期路径。
7. 定向测试用于日常小步迭代；跨层迁移完成和删除旧路径前必须运行全量构建与测试。

## 7. 分阶段修正计划

### 阶段 -1：停止伪成功和无效承诺

目标：在架构迁移前先消除会把错误请求包装成正常结果的行为。

工作项：

- 删除 `PlaceholderAnalysis` 的 Spot RMS 回退；未知分析键必须返回结构化 `UnknownAnalysis` 错误。
- 区分“有效数值为零”和“没有有效光线”，后者必须是明确失败或无数据状态。
- 对所有公开分析参数建立“参数确实进入规范请求并影响对应算法路径”的测试。
- 对尚未实现的 UI 参数选择以下一种处理：实现、禁用并标注原因、或从 UI/契约移除；禁止保留可选但无效的控件。
- 对 `IRayAimer` 模式做调用链和行为测试；若未接入主追迹，先从公开能力中移除，不再宣称支持多种模式。

验收条件：

- 未知分析、缺失实现和无有效数据都不能显示为普通成功数值。
- 每个可见参数都有从 UI/DTO 到算法读取点的自动化证据。
- 未实现能力不会出现在正式能力清单中。

回滚策略：错误类型和 UI 禁用可先兼容旧会话读取，但禁止恢复伪造数值结果。

以下阶段条目保留原始迁移检查表。已实现状态以文首“当前实施进度”和带日期的实施记录为准；条目中的将来时不表示对应旧类型仍存在。

### 阶段 0：冻结扩散并建立路径账本

目标：在不改变计算结果的前提下，找全所有入口和运行路径。

工作项：

- 建立“执行路径账本”，逐项登记文档、处方、分析、可视化、优化、公差、多配置和材料服务的公开入口、实际执行器、状态来源、默认值来源、快照方式、缓存和测试覆盖。
- 禁止新生产代码引用 `OptilandWorkbench.Application.Legacy`。
- 给分析和长任务结果增加仅用于诊断的来源信息：规范键、源修订号、请求指纹、执行器标识。
- 记录兼容入口调用计数，区分生产调用和测试调用。
- 修正架构文档措辞：明确 `OpticalWorkspaceModel` 仍是生产依赖，当前新服务并非完全独立实现。

验收条件：

- 每个生产入口都能追溯到唯一账本项。
- CI 能阻止新增的 Legacy 依赖。
- 任一分析结果都能回答“用哪份镜头、哪份请求、哪条执行链路算出”。

回滚策略：诊断元数据不得参与数值计算或序列化兼容，可独立移除。

### 阶段 1：收敛工作区状态与写入路径

目标：让 `WorkspaceCoordinator` 真正成为唯一工作区协调者，不再以旧模型事件作为间接状态协议。

工作项：

- 将 `OpticContext.Connector` 替换为明确的工作区状态对象，只持有当前 `Optic`、多配置状态、撤销栈和文档生命周期。
- 把修订递增、事件发布、自动半口径刷新、撤销/重做和取消令牌的责任集中到 `WorkspaceCoordinator`。
- 将处方、配置和系统设置的修改改为显式命令；命令必须声明 `WorkspaceChangeCategory`。
- 禁止领域服务直接获得可调用任意旧方法的 `Connector`。
- 为每种写操作增加“只递增一次修订、只发布一次事件、正确失效缓存”的契约测试。

验收条件：

- 新服务不再通过旧模型事件判断修改完成。
- 任何受支持入口修改镜头后，得到相同修订号、快照和事件序列。
- `OpticalWorkspaceModel` 不再拥有独立的当前镜头、撤销栈或多配置状态。

回滚策略：逐类命令迁移；未迁移命令暂时通过受控适配器委托，但适配器不得绕过协调器。

### 阶段 2：收敛分析链路

目标：所有分析入口使用同一个规范分析执行器。

工作项：

- 从 `OpticalWorkspaceModel.Analysis*` 提取与 UI/旧 DTO 无关的规范能力：分析键解析、参数描述、请求归一化、执行和结果映射。
- 建立单一 `AnalysisDescriptor` 注册表，集中提供规范键、工厂、参数、展示类型、能力声明和别名；Core、Application 与 GUI 不再分别维护 switch。
- `AnalysisService` 直接调用规范执行器，不再为快照创建 `OpticalWorkspaceModel`。
- 默认值分成“Core 通用默认值”和“Application 产品预设”，测试捕获的 Zemax 设置必须显式传入。
- `OptilandConnector.BuildAnalysisView` 改为纯兼容委托：旧参数映射为规范请求，再把规范结果映射为旧结果。
- 建立跨入口一致性矩阵，至少覆盖一阶数据、光斑图、单光线追迹、波前、MTF 和照度类分析。

验收条件：

- 规范分析执行器是生产环境中唯一能启动分析计算的入口。
- 新旧入口的规范请求指纹完全相同；结果的类型元数据、轴量纲、单位和数值通过一致性测试。
- `AnalysisService`、App 和兼容适配器不再包含第二份分析选择或默认值逻辑。

回滚策略：按分析族逐个切换；每个分析族保留短期可观测回退开关，但开关只用于定位回归，并在该阶段结束前删除。

### 阶段 3：逐域替换旧模型生产职责

按以下顺序迁移，前一项通过验收后再开始下一项：

1. 文档读写：提取格式适配器和规范 `LoadedOpticalDocument`，由 `OpticalDocumentService` 管理文件切换与保存生命周期。
2. 处方与组件：把表面、视场、波长、孔径、材料和组件操作改为显式命令。
3. 多配置：统一活动配置、基础镜头和配置切换后的修订语义。
4. 可视化：只消费规范快照和共享追迹结果，不创建私有工作区。
5. 优化：统一变量、评价函数预设、进度、取消、结果应用和撤销边界。
6. 公差：统一扰动快照、随机种子、嵌套并行所有权、补偿和结果应用。
7. 材料与本地化：把显示文本与领域标识分离，删除对旧模型显示辅助方法的依赖。

在领域服务迁移之外，Core 必须并行完成两项“单一真相来源”收敛：

- `OpticalSurface` 选定组合对象为规范状态；旧标量/字符串属性在兼容期只能是无状态投影或受控适配器，不能继续双向独立保存。
- 光线生成只保留一套 Telecentric、Apodization 和 Ray Aiming 权威状态与执行路径，禁止旧设置和新模型叠加生效。

每个领域的统一验收模板：

- 新服务不引用 Legacy 类型；
- 兼容入口只调用新服务或规范执行器；
- 没有独立状态、默认值、缓存或任务生命周期；
- 新旧入口契约测试通过；
- 对应文档已从“计划行为”更新为“已实现行为”。

### 阶段 4：隔离兼容层

目标：旧 API 即使暂时保留，也不能参与新架构内部实现。

工作项：

- 将 `OptilandConnector` 和剩余旧 DTO 移入独立兼容边界；条件允许时建立单独程序集。

- 兼容层中不存在 Core 分析、追迹、优化或公差执行器的直接构造。

目标：完成退场，而不是永久保留“以后再删”的旧系统。

验收条件：

- 同一镜头经 GUI、新服务和仍受支持的兼容 API 得到相同规范请求与结果。
- 架构测试、跨入口一致性测试、全量构建和全量测试全部通过。

## 9. 测试与 CI 闸门

### 9.1 架构测试

新增或加强以下规则：

- `OptilandWorkbench.App` 不得引用 `Application.Legacy` 或 Core。
- Application 的主服务不得引用 `Application.Legacy`。
- 兼容层不得被 `Services`、`Contracts` 或组合根反向引用。
- 只有规范执行器可以启动 Core 分析、优化和公差计算。
- 旧 API 不能拥有可变工作区状态、缓存或后台任务。
- “薄兼容层”测试必须检查完整依赖和委托关系，不能只检查子类有没有声明方法。

### 9.2 跨入口一致性测试

同一测试夹具至少通过以下入口执行：

- `IWorkbenchApplication` 正式入口；
- GUI 使用的服务请求入口；
- 仍受支持的兼容 API；
- 规范执行器的直接契约测试。

比较内容包括：

- 规范请求指纹；
- 镜头修订号和快照内容指纹；
- 分析类型、轴量纲、单位、系列和有效状态；
- 数值结果及明确的逐项容差；
- 异常、取消和无效光线语义；
- 缓存命中不改变结果；
- 保存、重开、多配置切换和撤销/重做后的结果。
- 修改 `OpticalSurface` 的旧兼容属性或规范组合对象后，规范快照和追迹结果不能出现双状态。
- Ray Aiming、Telecentric 和 Apodization 的每个公开模式必须有可观察、符合定义且唯一的执行路径。

夹具至少覆盖：

- 当前提交的 Zemax OpticStudio 2026 R1 `123456.ZMX` 基线及其捕获设置；
- Cooke 与 Tessar 辅助回归镜头；
- 有限物距、无限物距、多视场、多波长和多配置；
- 会触发全反射、渐晕、无效交点或数值失败的边界样本。

### 9.3 验证节奏

- 单文件或单分析族迁移：运行对应定向测试和架构测试。
- 一个领域迁移完成：构建整个解决方案，并运行该领域测试集合。
- 跨层依赖改变、删除旧路径、阶段验收或准备推送：执行全量构建和全量测试。
- 不要求每个机械小改动都运行全量测试，但不得用定向测试代替阶段出口验证。

## 10. 提交与评审规则

每个收敛提交必须回答：

1. 本提交消除了哪一条旧运行路径？
2. 新的唯一执行器在哪里？
3. 默认值、快照、修订、缓存和结果映射由谁负责？
4. 兼容入口现在是委托、仅测试还是删除？
5. 哪个跨入口测试证明结果没有因入口不同而变化？
6. 是否引入临时开关？若有，其删除版本和删除条件是什么？
7. 文档中的内容是已实现、兼容行为还是计划行为？

禁止以“文件已经拆小”“类已经改名”“接口已经增加”作为架构收敛完成的证据。完成证据必须是运行路径消失、依赖方向正确和跨入口结果一致。

## 11. 首个迭代（历史计划）

首个迭代只做四件事：

1. 完成执行路径账本，并把现有生产 Legacy 依赖固定为只减不增的允许清单。
2. 删除未知分析的伪结果回退，并为无数据状态建立明确契约。
3. 建立规范请求与结果来源指纹，不改变数值算法。
4. 建立跨入口一致性测试框架，以“一阶数据 + 光斑图 + 单光线追迹”为首批样本。
5. 设计并评审新的工作区状态所有权与 `OpticalSurface` 单一真相来源，确定分步退场边界。

该历史迭代结束时不要求删除全部旧代码，但必须让当时的双轨现状可见、可测、不可继续扩散，并为下一迭代迁移分析链路提供可靠基线。2026-08-24 已完成生产 Services 的单轨运行时迁移。

## 12. 最终退出条件

只有同时满足下列条件，才能宣布问题修复完成：

- App 和 Application 主服务均不引用 Legacy。
- `WorkspaceCoordinator` 是唯一写入、修订和生命周期协调入口。
- 每个分析、优化、公差和可视化任务都从规范快照及规范请求启动。
- 默认值、名称解析、DTO 映射和缓存策略各只有一个权威来源。
- 未知功能、未实现参数和无有效数据不会被包装为成功结果。
- 光学表面、Telecentric、Apodization 和 Ray Aiming 不存在两套可变状态或互不连接的执行路径。
- 兼容层无状态、无计算，并已删除或有明确的外部兼容期限。
- 跨入口一致性矩阵全部通过，同一镜头不再因入口不同得到不同结果。
- 全量构建、全量测试、架构测试和文档检查通过。
